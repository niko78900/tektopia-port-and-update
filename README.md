# TekTopia Port and Update

Community maintenance and porting workspace for TekTopia.

The active work is a Forge `1.16.5` port under `port-1.16.5/`. The repository also keeps the older decompiled `1.12.2` patch workspace for reference and bridge-build maintenance.

## Status

- Active target: Minecraft Forge `1.16.5-36.2.42`
- Mod id: `tektopia`
- Current port version: `1.16.5-alpha.2`
- Current estimate: `93-95%` implementation parity
- Release state: build-green implementation candidate, not a validated 100% release

The current 100% release gate is still blocked by live runtime validation: client visual boot, spawn-every-entity QA, multi-world starter worldgen checks, a 30-minute singleplayer soak/reload pass, two-client multiplayer validation, and 1/3/5-village performance runs.

## Features In The 1.16.5 Port

- Forge 1.16.5 project with modern registries, entities, items, containers, networking, commands, and saved data.
- Tek villager professions including guard, farmer, blacksmith, miner, lumberjack, chef, rancher, butcher, merchant, nomad, architect, tradesman, teacher, bard, cleric, druid, enchanter, child, and nitwit.
- Village runtime for structures, residents, storage/economy, reservations, alerts, raids, and worker status.
- Player-facing villager GUI with Main, AI Filters, Village, Storage, and Trade tabs.
- Server-authoritative packets for AI filters, villager snapshots, village/storage/trade GUI snapshots, path debug, thoughts, item thoughts, and trade actions.
- Controlled starter structure generation and scanner-compatible structure tokens.
- Internal CraftStudio-style model loader and renderer path with recovered Guard assets and recreated coverage for other registered entities.
- QA commands for parity, sync, assets, worldgen, performance, economy, workforce, reservations, pens, trades, and raids.

## Requirements

- Windows with PowerShell
- JDK 17 available to run ForgeGradle
- Local Forge/Minecraft dependency caches generated by Gradle
- For the legacy `1.12.2` patch workspace: the original base TekTopia jar and local dependency jars under `tooling/libs/`

The 1.16.5 port is the normal Gradle project. The older `decompiled/` tree is not expected to clean-compile as a full project.

## Build The 1.16.5 Port

```powershell
cd .\port-1.16.5
.\gradlew.bat clean compileJava --rerun-tasks
.\gradlew.bat build
```

Build a reobfuscated release jar:

```powershell
cd .\port-1.16.5
.\gradlew.bat releaseJar -Ptektopia_enable_reobf=true
```

Output jars are written to:

```text
port-1.16.5/build/libs/
```

## Run Development Instances

Client:

```powershell
cd .\port-1.16.5
.\gradlew.bat runClient
```

Server:

```powershell
cd .\port-1.16.5
.\gradlew.bat runServer
```

## QA Gates Before 100%

The hard 100% release-candidate checklist is in:

```text
docs/PORTING_1.16.5_100_RC_QA.md
```

At minimum, a 100% claim requires:

- clean compile, build, and release jar
- client boot with no missing model/texture errors
- strict asset inventory pass
- every registered Tek entity spawned and visually checked
- natural starter worldgen validation across multiple worlds
- 30-minute singleplayer soak with reload cases
- dedicated two-client multiplayer validation
- 1-, 3-, and 5-village performance runs

## Legacy 1.12.2 Patch Builds

The `1.12.2` workspace is retained for bridge releases and historical patch work. It uses a targeted patch-build script instead of a normal Gradle source set.

Example:

```powershell
powershell -ExecutionPolicy Bypass -File .\build-release-1.1.1.ps1 `
  -BaseJar .\tektopia-1.1.0.jar `
  -Version 1.1.3 `
  -OutJar .\out\tektopia-1.1.3.jar
```

Use the Forge 1.12.2 runtime and CraftStudio API dependency when testing these legacy jars.

## Development Notes

- Keep work on `main`; `origin/main` is the canonical branch.
- Keep commits scoped by feature or QA chunk.
- Do not treat build success as 100% parity. Runtime QA evidence is required.
- Keep manual frame/token discovery working even as starter worldgen improves.
- Avoid adding a required runtime animation dependency; CraftStudio compatibility is implemented internally.
